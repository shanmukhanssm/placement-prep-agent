# ADR-001: placement-prep-agent — handoff-router graph with three specialist subgraphs and file-based report card

**CONTEXT:** A single-user (one BTech student) placement-preparation coach. The student chats in; on first run the agent onboards him (name, branch, grad year, target roles, weak areas, core subject — chosen once at onboarding and fixed afterwards), and on every return visit narrates his improvement trend from recorded test numbers, then routes the conversation to one of three specialist practice sessions: DSA (2 internal roles — selector picks one problem per session, evaluator judges attempts and passes at ≥80% of the optimized approach or on give-up, max 3 attempts), Communication (HR-style interviewer, 8–10 non-subject questions, per-answer rubric scoring), Core Subject (examiner, 8–10 questions on the chosen subject incl. DSA theory, per-answer scoring). All scores land in a file-based report card (`data/report-card.json` + per-session history files + rendered `REPORT_CARD.html`, HTML in v1 scope, template designed with the owner later). Trends are computed by deterministic Python, never by the LLM. LLM: Groq via OpenAI-compatible endpoint (model placeholder `llama-3.3-70b-versatile`, env-overridable; exact model choice deferred). Quality bar: correct trend math always; honest, rubric-anchored scoring; the agent counts as done only after the full eval suite passes across multiple repeated runs. Volume: one human, a few sessions/day. Latency tolerance: conversational (seconds per turn).

**Feasibility gate (7-question checklist):** decomposition unpredictable (intent-driven) YES · more than one model call needed YES (classify / generate / judge are distinct calls) · observable feedback signal YES (user answers, recorded scores) · variable latency tolerable YES · worst-case cost bounded YES (session caps: ≤10 questions, ≤3 DSA attempts, recursion limit) · eval coverage planned YES · failure cost asymmetric in our favor YES (worst case: one glitched question, no money, no irreversible actions). **Verdict: 0 "no" — build the agent.**

**DECISION:**
- **Pattern stack (smallest that meets the bar):** Routing → specialist loop (tool use + evaluator) → deterministic recording. Routing because input classes are distinct (dsa / communication / core / progress-talk / smalltalk / exit / unclear→clarify). Evaluator-optimizer inside each specialist because explicit rubric criteria exist. Deterministic file tools (no RAG) for report-card facts. Explicitly rejected: planning, reflection, fan-out, agentic RAG — no framework question justifies them.
- **Topology:** handoff router (routing with state-carrying transitions), implemented as **one mono-graph + three compiled specialist subgraphs + one onboarding flow** — not supervisor multi-agent. Justification per subgraph: each specialist has a materially different persona prompt, rubric, and loop shape; one mega-prompt would blur rubrics and bloat context. When-NOT check for handoff router passed: low category overlap (comm is explicitly non-subject, core owns theory incl. DSA theory), routing pinned by `session_active` state so mid-session follow-ups never re-classify, explicit clarify bucket for ambiguous intents.
- **Interaction model:** turn-based chat — every user message is one graph invocation against a checkpointered thread (SQLite, thread-per-session); the graph ends its turn whenever it needs user input. No `interrupt()` in v1; the CLI loop is the human gateway. Specialists are cross-turn state machines (a `phase` field), so a DSA attempt or the next interview question arrives as the next invocation.
- **Agency dial:** L1 (model decides within code-owned loops) on router classification, question generation, answer judging — each with structured output + validation + one retry. L0 (deterministic) on trend math, all file reads/writes, session bookkeeping. L3 nowhere — no irreversible actions, no external side effects; the only writes are to the user's own data directory.
- **Framework:** LangGraph (mandated by the parent workflow; scorecard for durable multi-step product weights: graph control 5, state/durability 5, HITL 5 — dominates). Framework-agnostic core enforced: tools are plain typed Python functions; report card JSON is the system of record; prompts live in `prompt-registry.md`; the LLM client is `ChatOpenAI(base_url=$LLM_BASE_URL)` so any OpenAI-compatible provider is an env-var swap.
- **Platform maturity target:** L2 (durable, checkpointed, hand-resumable). Tracing/metering (L3+) deferred to the operate stage.

**ALTERNATIVES CONSIDERED:**
- Single mega-prompt chatbot: rejected — three different rubrics and loop shapes in one prompt degrade judging quality and exceed one coherent system prompt.
- Supervisor/worker multi-agent: rejected — supervisor token tax and non-deterministic routing for a job conditional edges do deterministically.
- Long-running graph with `interrupt()` per question: rejected for v1 — turn-based invocation with a checkpointer gives the same durability without resume-semantics sharp edges; revisit only if a web/API deployment needs server-side pause/resume.
- Vector store / RAG for question banks: rejected — question generation is generative, and profile/history facts are small structured JSON read by tools.
- Framework bake-off (LangGraph vs Pydantic AI, 2-day hard slice): deferred until after the Phase 0 skeleton (dated re-check); LangGraph is the parent workflow's mandate, so the bake-off only guards against a surprise mismatch.

**CONSEQUENCES:**
+ Specialist quality: each rubric lives in its own small prompt and subgraph; router errors are cheap and recoverable (clarify loop).
+ Trend integrity by construction: numbers are computed by unit-tested Python; the LLM only narrates them, so the "am I improving" answer cannot be hallucinated.
+ Durability for free: checkpointer threads survive restarts mid-session; per-question score writes are idempotent, so a crashed session keeps answered scores.
− Routing is LLM-based (per the owner's "no commands, human vibe" requirement): classifier error fans out — mitigated by low category overlap, confidence + clarify bucket, and an intent eval set with a ≥95% accuracy gate.
− Score noise is trend noise: mitigated by rubric anchoring, temperature 0.2 judges, structured-output validation, and a judge-consistency eval (same answer twice → ±1 point).
**Budgets:** latency ≤3 LLM calls per turn, p95 turn < 8s on Groq · cost ≈ 12 calls/session ≈ ~40k tokens/session → $0 on Groq free tier at single-user volume; paid fallback <$5/month; if rate-limited, judges drop to `llama-3.1-8b-instant` (tiering lever, decision parked) · reliability per-step 0.95 assumed, ~0.99 with validation-retry → session ≈ 0.89 honest end-to-end — accepted because failures are cheap (per-question records survive, worst case one repeated question) · safety: no approval gates needed (no irreversible actions; CLI user is the human).

**EVIDENCE (filled in after 30 days):** measured tokens+cost per session; intent-classification accuracy on logged utterances; judge score distribution vs anchor bands; termination-reason distribution of DSA sessions (pass / give-up / max-attempts); eval suite pass rate across repeated runs.

**Eval plan commitment:** golden E2E cases (1: brand-new user onboarding → first DSA session; 2: returning user → trend narration → DSA session to pass or give-up; 3: full communication session, 8–10 questions scored) run across **3 repeated runs, all green** (owner's "evaluated multiple times" bar); intent test set ≥24 utterances incl. ambiguous, ≥95% accuracy with zero unwaived misroutes; judge-consistency set ≥10 sampled answers. One metric per pattern: router accuracy, judge consistency, session-completion rate, trend-math property tests.

**Build sequencing (maps the advisor's 30-day arc onto the project's Build Ladder):** Week 1 = Phase 0 skeleton (stub graph end-to-end on fake input) + eval gate harness; Week 2 = Phase 1 real tools + trend math; Week 3 = Phase 2 specialist subgraphs one at a time (onboarding → comm → dsa → core), each gated; Week 4 = Phase 3 real router wiring + HTML report-card render, then Phase 4 eval suite + repeat-run gates, then the harden stage (reliability pass, guardrail spec, eval CI).
